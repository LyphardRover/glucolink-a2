## 第二阶段 你交出去的脚本在做什么

### A 建库与重新连接

`B_create_database.psql` 是给 psql 这个命令行工具的文件。它先看 glucolink_a2 是否存在；没有才执行 CREATE DATABASE。反斜杠开头的命令属于 psql，不是所有 SQL 编辑器都认识。

`B_create_database.sql` 是给 CloudBeaver 这类普通 SQL 编辑器的替代文件。只在库不存在时单独执行 CREATE DATABASE，不要把它放进 BEGIN/COMMIT。

**重新连接**就是告诉操作工具：后面的语句要进入新文件柜。创建完库，并不意味着当前窗口自动切到它。B_run_setup.ps1 会把建库和建分区分成两次数据库连接。

### B B_setup.sql 的四个小部分

1. `BEGIN`：把这一批建 schema 的操作作为一个事务处理。你可以理解为把这一批操作作为一个整体准备。
2. `current_database()` 检查：先核对正在操作哪个文件柜。连错就 `RAISE EXCEPTION` 报错停止，避免把项目分区建进练习库。
3. 八行 `CREATE SCHEMA IF NOT EXISTS`：抽屉没有就创建，有了就保留。它不会创建业务表，也不会导入数据。随后检查当前角色是否能使用并在这些分区中创建对象。
4. `COMMIT`：正常完成后确认这一批操作。如果交互式窗口途中报错，先 `ROLLBACK` 退出失败事务，再修正连接重试。

### C 只读检查

`00_environment_check.sql` 读取版本、当前数据库和分区信息。

`B_verify_setup.sql` 检查目标数据库与八个分区，应该看到 PASS，并给出统一的版本标记和分区列表。刚完成 B 的空框架时，业务表/视图数量是 0；C/D/E 开始建表后，数量增加是正常的。

`B_capture_baseline.sql` 读取结构，保存快照作为下次比较起点。它不是完整数据备份，也不会自动告诉我们谁改了什么。

## 第三阶段 三张图分别告诉老师什么

### 第 1 页 架构图

回答“系统分成哪些部分，谁负责”。左边三个来源经过 raw、cleansed、curated，到 reporting。audit 计划记录处理过程。上方标出了 A 到 F 的职责。

八个分区真实存在。框里写的业务处理仍为 pending，不能把箭头读成“数据已经跑过去了”。箭头表示设计中的处理顺序。

### 第 2 页 概念模型

回答“业务里有哪些东西，它们是什么关系”。一个真实的虚构患者可能在 GP、病理和药房各有一条来源记录；这些来源记录的编号通常不同。匹配程序要判断哪些记录属于同一个人。

有些记录证据不够，就保留 unresolved，不能强行归到某个人名下。一个来源患者记录可能关联多次就诊、检验或配药事件。UC3 计算使用检验事件，三来源参与的是身份关联。

### 第 3 页 小逻辑模型

回答“准备使用哪些表、字段和编号把数据接起来”。

| 表 | 把它当作哪一种登记表 |
|---|---|
| patient_master | 一个人登记一行的统一身份表 |
| patient_source_link | 记录某来源的某编号对应哪个统一身份 |
| lab_results_clean | 每个整理后的检验事件登记一行，附质量结果 |
| dim_patient | 供分析使用的患者登记表 |
| fact_lab_result | 每个纳入分析的检验事件登记一行 |

`vw_uc3_hba1c_trend` 是计划中的查询视图，利用事实表和患者维度算出每个人的首末检验值与变化。视图可以理解为保存了一份查询规则；它不是另外手工抄出的答案。

### 三个新术语

- **主键 PK**：区分同一张表每一行的编号。例如统一身份表用 trusted_patient_id。
- **外键 FK**：引用另一张表已有的编号。例如检验事实中的 patient_key 指向患者维度。这能防止引用不存在的患者维度行，但不能证明患者匹配正确。
- **粒度 grain**：这一张表“一行到底代表什么”。患者维度是一人一行；检验事实是一项检验事件一行。

图里的 `0..1` 表示“可以没有，最多一个”；`0..many` 表示“可以没有，也可以多个”。`FK?` 表示允许空值的外键；虚线表示逻辑关联或派生查询，不表示已建成数据库约束。

### 一个仅供理解的例子

假设已经确认 GP 的 G01 与病理的 L09 都属于统一患者 P01，则来源关联表可以有两行：GP/G01→P01、PATH/L09→P01。患者维度给 P01 一个本机分析编号，例如 12。

如果 L09 有两次合格检验，事实表就有两行，两行都引用 patient_key=12。趋势查询再把这两次检验比较。**这些编号和记录只是教学例子，没有写入当前数据库。**

不能只看 G01、L09 这种来源编号就判断是不是同一个人；也不能把不同电脑产生的 patient_key=12 当作同一个患者。

### 为什么要这样设计

原始数据保留一份，清理后的数据另放，分析表再明确每行含义，出问题时比较容易定位。例如结果被算了两次，可以核对 raw 的重复记录、D 的去重结果与 E 的事实表。

代价是多存几层数据，并且必须维护每一步的脚本、版本和交接顺序。这是你可以向老师解释的一项设计取舍。
